# Multi-Agent Research System: спостережуваність через Langfuse

Розширення попередньої роботи. **Система не змінилась**: ті самі MCP-сервери для
інструментів, ті самі три A2A-агенти, той самий цикл Plan → Research → Critique з
лімітом доробок і людиною перед записом. Додалося те, чого не було: **видимість**.

Три речі за завданням — наскрізний trace, промпти в Prompt Management, автоматична
оцінка нових трейсів. Але найцікавішим виявилось не жодне з них.

**Найважче було зшити дерево через процеси.** Агенти живуть у різних процесах за
A2A, а трасування сетевий виклик не переживає: кожен процес почав би свій trace, і
замість дерева в інтерфейсі лежали б чотири незвʼязані корені. Розділ про це —
нижче, і він найдовший.

**А найважливішим виявилось те, чого завдання не просить узагалі** — розділ про
приватність відразу за швидким стартом. Стандартна інтеграція відправляє третій
стороні значно більше, ніж потрібно тій стороні для роботи.

Текст завдання — у [TASK.md](TASK.md).

## Швидкий старт

```bash
cd "Homework 12"

python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env       # OPENAI_API_KEY + ключі Langfuse

python prompts_seed.py     # промпти → Langfuse (одноразово)
./start_servers.sh         # Qdrant + 2 MCP + 3 A2A
python main.py
```

Без ключів Langfuse система працює як працювала, просто мовчки: `enabled()`
віддає `False`, усі хелпери стають пустушками. **Телеметрія, без якої продукт не
піднімається, — найгірший вид телеметрії.**

## Попередження: третя сторона отримує більше, ніж їй потрібно

Це головне, що варто винести з цієї роботи, і завдання про це не згадує.

Langfuse робить корисну справу: показує дерево викликів, латентність, вартість,
де саме прогін пішов не туди. Щоб це робити, йому потрібні **структура викликів,
таймінги й лічильники токенів**. Зміст твоїх документів для цього не потрібен.

Але стандартна інтеграція відправляє в хмару **все**:

| що їде | навіщо це Langfuse | навіщо це тобі |
|---|---|---|
| латентність, токени, вартість | по суті задачі | по суті задачі |
| дерево викликів, імена інструментів | по суті задачі | по суті задачі |
| повні входи й виходи LLM | не потрібно для метрик | зручно для налагодження |
| **результати викликів інструментів** | **не потрібно** | зручно |
| `session_id`, `user_id`, теги | по суті задачі | по суті задачі |

Третій рядок знизу — той, через який варто зупинитись. Результат
`knowledge_search` — це **пасажі з корпусу разом з іменами файлів і сторінками**.
На цій демонстрації там три публічні PDF про RAG, і боятися нема чого. Наведи ту
саму систему на особистий індекс — і в чужу хмару поїде справжнє листування з
іменами контрагентів, сумами й термінами.

Непропорційність тут не в тому, що хост чужий. Вона в тому, що **дані, які
збираються, не стосуються задачі, яку ця сторона виконує**. Для побудови графіка
латентності не потрібен текст договору.

### Що зроблено: маска на тому ж списку, що охороняє git

У проєкті вже є перелік того, що не має покидати машину — `.private-names.txt`, за
яким `pre-push` блокує публікацію в GitHub. Охороняти ним git і не охороняти
телеметрію — непослідовно: витік через трейс нічим не кращий за витік через коміт,
тільки помітити його не можна взагалі.

Тому клієнт Langfuse піднімається з `mask=`, і маска бере **той самий файл**:

```
до :   У листі від Вигадонікс йдеться про строки.
після: У листі від В********с йдеться про строки.
```

Приклад тут навмисно з вигаданою назвою, і на це є причина. У першій редакції
цього розділу стояло справжнє ім'я зі списку — і `pre-push` зупинив публікацію,
показавши рядок 78 цього ж файлу. Тобто пояснюючи, як не допустити витоку, я його
й влаштував; врятувала автоматика, а не уважність.

Це і є аргумент за ворота сильніший за будь-який теоретичний: **той, хто пише про
маскування, помиляється в маскуванні.**

Зіставлення повторює `check_names.py` — по основі з межею слова, без урахування
регістру, тож ловляться й відмінкові форми, на яких ручне маскування колись
прокололось. Маска рекурсивна: проходить вкладені словники й списки, тобто чистить
і результати інструментів, а не лише текст відповіді.

Один список, двоє воріт.

### Чого маска НЕ робить, і що робити натомість

Маска знає рівно ті імена, які в списку. Тему листа, суму, номер договору, дату
зустрічі вона не приховає — і не може.

Тому для роботи з особистим корпусом правильна відповідь не маска, а **свій
Langfuse**. Він піднімається локально й нічого назовні не віддає:

```bash
git clone https://github.com/langfuse/langfuse.git
cd langfuse && docker compose up -d          # UI на localhost:3000
```

Далі в `.env` міняється рівно один рядок:

```bash
LANGFUSE_BASE_URL=http://localhost:3000
```

Той самий SDK, той самий інтерфейс, ті самі Prompt Management і LLM-as-a-Judge.
Код не змінюється **жодним рядком** — і це, мабуть, найкращий аргумент на користь
того, що адресу бекенда варто тримати налаштуванням, а не вважати даністю.

Ця робота свідомо зроблена на хмарі: корпус публічний, а здавати треба скріншоти з
їхнього інтерфейсу. Для будь-чого свого — self-host.

### Ще дві ручки, які варто знати

`tracing_enabled=False` вимикає відправку цілком, не чіпаючи код. `sample_rate`
шле частку прогонів — розумно, коли трейси потрібні для статистики, а не для
розбору кожного випадку.

## Архітектура

```
User (REPL, main.py)
  │   propagate_attributes(session_id, user_id, tags)  ← корінь trace
  ▼
Supervisor  (create_agent + HumanInTheLoopMiddleware + CallbackHandler)
  │
  ├── delegate_to_planner    ──► A2A :8923 ─┐
  ├── delegate_to_researcher ──► A2A :8924 ─┤ metadata: trace_id + parent_span_id
  ├── delegate_to_critic     ──► A2A :8925 ─┘
  │        └─ TraceContext → CallbackHandler → гілка під батьком
  └── save_report            ──► MCP :8922 ReportMCP   (через HITL)

           усі троє ──► MCP :8921 SearchMCP (кросс-енкодер один на всіх)
```

Порти **8921–8925**, розведені з попередніми роботами. Урок, засвоєний дорого:
поки адреса одна, працює той, хто встиг першим, і тести однієї роботи непомітно
міряють сусідню.

### Дерево через межі процесів

Головна інженерна задача роботи.

Langfuse 4.x стоїть на OpenTelemetry, а там належність до дерева задається парою
чисел: `trace_id` — спільний на все дерево, і `span_id` батька. Отже, щоб виклик
суб-агента став гілкою, а не новим коренем, ці два числа треба довезти до іншого
процесу.

**Клієнт** (`a2a_utils.py`) кладе їх у `metadata` повідомлення — три рядки:

```python
carrier = observability.carrier()
if carrier:
    message.metadata.update(carrier)
```

**Сервер** (`a2a_servers.py`) читає їх із `RequestContext.metadata`, збирає
`TraceContext` і віддає в `CallbackHandler`:

```python
trace_ctx = observability.trace_context(context.metadata)
result = await agent.ainvoke(..., config={"callbacks": observability.callbacks(trace_ctx)})
```

Чому через `metadata`, а не через заголовок `traceparent`, як пропонує W3C: у A2A
повідомлення **має власне поле** `metadata` (`google.protobuf.Struct`), тобто
протокол уже передбачив місце для «даних про запит, що не є запитом». Заголовок
живе рівнем нижче протоколу й загубиться при зміні транспорту на gRPC; metadata
переживе.

Немає контексту — агент почне свій trace, і це правильна поведінка, а не помилка:
означає, що його покликали напряму, повз супервізора.

### Дві поломки, які не падають

Обидві коштували години й належать до одного класу: система працює, дані йдуть,
помилок немає — і лише в інтерфейсі видно, що дерева немає. Такі знаходяться
тільки перевіркою результату, а не читанням логів.

**1. Контекст не переживає `async def`.**

Перша версія брала поточний спан з OpenTelemetry і покладалася на те, що він є.
У **синхронному** інструменті він справді є; в **асинхронному** — ні. Заміряно:
той самий `carrier()` із синхронного інструмента віддає пару чисел, з
асинхронного — порожній словник.

Причина в тому, що `CallbackHandler` робить свій спан поточним лише на час
власних синхронних колбеків. Тіло асинхронного інструмента виконується пізніше й
поза цим вікном — а наші делегування по A2A саме `async def`, бо LangGraph
асинхронний.

Лікується не підпоркою, а зміною підходу: **контекстом треба володіти**. Свій
`root_span` на весь запуск, знятий `carrier()` там, де він гарантовано є, і далі
явним параметром до кожного делегування. Ніякої залежності від того, що фреймворк
робить із контекстом усередині.

**2. У A2A два поля `metadata`, і сервер віддає не те, яке здається.**

У `Message` є своє поле `metadata`, у `SendMessageRequest` — своє. Логічно класти
контекст у повідомлення: він же про це повідомлення. Але сервер віддає в
`RequestContext.metadata` метадані **запиту**:

```python
@property
def metadata(self) -> dict[str, Any]:
    if self._params:
        return json_format.MessageToDict(self._params.metadata)
    return {}
```

Поклади в повідомлення — і на тому кінці буде порожньо. Запит піде, агент
відповість, у логах чисто. Розсипані корені в інтерфейсі — єдиний симптом.

Правильне місце — запит:

```python
request_message = SendMessageRequest(message=message)
if ctx:
    request_message.metadata.update(ctx)
```

### Session тримається навколо всього циклу підтверджень

`propagate_attributes` стоїть навколо **всього** `run_once`, а не одного
`ainvoke`. Інакше правка звіту людиною породжувала б другий trace, і один розмовний
захід виглядав би в інтерфейсі як два незвʼязані запуски.

### `flush()` перед виходом

Експорт асинхронний. Процес, що завершився одразу після відповіді, увозить хвіст
траси з собою — і в інтерфейсі виявляється обрізане дерево без жодної помилки в
логах.

### Літерал відповіді людини — рядок, який ніхто не звіряє

Помилка, знайдена перевіряючим уже після здачі попередньої роботи; код сюди
приїхав копією, тож вона була й тут.

`_ask_human` повертав `{"type": "accept"}`. Middleware звіряє літерал **рядком** і
знає лише `approve` / `edit` / `reject` / `respond`; незнайоме значення дає
`Unexpected human decision`. Жива людина, яка натиснула «так», отримала б падіння.
Docstring двома рядками вище казав правильно — код суперечив власній документації.

**Чому це пережило наскрізний прогін.** Тест підміняв `_ask_human`
автопідтвердженням, і те повертало ПРАВИЛЬНИЙ літерал. Я замінив рівно ту
функцію, у якій сиділа помилка, і перевірив усе, крім неї.

Це класична сліпа зона моків: підміняючи інтерактивну частину, підміняєш і її
контракт. Звідси правило, варте більше за саме виправлення:

> **Якщо щось замінюється моком заради тестованості — саме воно зобовʼязане
> перевірятися окремо.**

Тому поруч зʼявився `check_hitl.py`: тридцять рядків, жодного агента, жодного
токена. Три відповіді людини проганяються через справжній `_ask_human`, а
результат — через справжній `_process_decision`.

```
$ .venv/bin/python check_hitl.py
  ✓ approve  -> approve  инструмент исполняется
  ✓ edit     -> reject   не исполняется, модель правит
  ✓ reject   -> reject   не исполняется, модель останавливается
```

Зауваж, як це римується з двома німими поломками трасування вище: **усі три не
падали там, де їх шукали.** Дві ховалися в інтерфейсі Langfuse, третя — за
власним моком.

## Промпти як дані, а не як код

Вимога завдання: «у коді жодних захардкоджених system prompts». Виконано буквально
— в жодному `.py` цього репозиторію немає тексту системного промпту. Заразом
видалено `SYSTEM_PROMPT` одноагентної версії: він приїжджав ланцюгом копій з
Agent_1, не використовувався ніким, але формально лишався останнім.

Тексти лежать у `prompts_seed.json` і заливаються скриптом `prompts_seed.py`.
**Скриптом, а не руками в UI**, і не з лінощів:

- **відтворюваність** — розгорнути систему на чистому проєкті Langfuse це одна
  команда, а не чотири форми з копіпастом;
- **джерело правди** — тексти в git, з історією. Промпт, що живе тільки в хмарі,
  неможливо відревʼювити в pull request;
- **чесність міграції** — видно, ЩО саме поїхало.

Після заливки система читає промпти з Langfuse і в `prompts_seed.json` більше не
заглядає. Це дані міграції, а не конфігурація застосунку.

### Що змінюється від такого переїзду

Промпт перестає бути частиною збірки й стає **даними з версією та лейблом**.
Правка не потребує деплою, відкат — це перевісити лейбл, а не шукати текст в
історії чату. `create_prompt` з тим же іменем створює **нову версію**, стара
лишається.

Trace звʼязується з версією промпту через `propagate_attributes(prompt=…)`. Без
цього в інтерфейсі видно «відповідь стала гіршою», але не видно, що напередодні
поміняли третій рядок системного промпту.

Плата названа прямо: система тепер не піднімається без мережі до Langfuse. Це
реальна нова залежність, і для продакшену вона вимагала б кешу з падінням на
останню відому версію.

## Приклад роботи

Три прогони однією сесією:

```
$ .venv/bin/python main.py
трейси: https://us.cloud.langfuse.com | session=repl-20260825-004025 | user=vl

You: Compare RAG approaches: naive, sentence-window, and parent-child
[Supervisor → A2A → Planner]      [planner]    2 863 токенов
[Supervisor → A2A → Researcher]   (раунд 1)
[Supervisor → A2A → Critic]       ← вердикт: REVISE
[Supervisor → A2A → Researcher]   (раунд 2)
[Supervisor → A2A → Critic]       ← вердикт: REVISE
[Supervisor → A2A → Researcher]   (раунд 3)
⏸️  ТРЕБУЕТСЯ ПОДТВЕРЖДЕНИЕ → approve
```

Те, що дерево справді зшилося, перевірено **через API, а не на око** — обидві
поломки вище були німими, і довіряти інтерфейсу без перевірки означало б повторити
ту саму помилку:

```
трейс bc43b5772a34…  спостережень: 313
  типи: CHAIN 165, TOOL 105, GENERATION 42, AGENT 1
  коренів усередині трейсу: 1  →  ['multi-agent-research']

  найчастіші вузли:
    105  tools
     48  read_url          ← виклики інструментів СУБ-АГЕНТІВ
     45  web_search           з інших процесів
     42  ChatOpenAI
     10  HumanInTheLoopMiddleware.after_model
      4  knowledge_search
      3  delegate_to_researcher
      3  delegate_to_critic
      1  save_report
      1  multi-agent-research
```

Порівняй із тим, що було **до** виправлення: у трейсу супервізора було 23
спостереження, а поруч лежали окремі корені на 105 і 121 — суб-агенти, які
почали власні дерева. Тепер один корінь і 313 вузлів під ним; 275 і 459 у двох
інших прогонах тієї ж сесії.

Усі три мають `session='repl-20260825-004025'` і `user='vl'` — вимога про
групування виконана не декларативно, а перевірена запитом до API.

## Обмеження

- **Маска захищає від відомого, не від невідомого.** Див. розділ про приватність.
- **Промпти стали мережевою залежністю.** Немає звʼязку з Langfuse — система не
  стартує. Ціна за те, що промпт можна правити без деплою.
- **Оцінка налаштовується в інтерфейсі, а не кодом.** Evaluator'и LLM-as-a-Judge
  заводяться руками в UI; на відміну від промптів, у git їх не покладеш.
- **Латентність експорту.** Оцінка виконується асинхронно: між прогоном і появою
  score минає хвилина-дві. Для CI це означає, що на неї не можна чекати синхронно.
- **Три агенти в одному процесі.** Знадвору це три незалежні сервери з трьома
  картками; спільний у них лише інтерпретатор.
- **Вкладеність суб-агентів — під корінь, а не під конкретний виклик.** Контекст
  знімається один раз у `root_span`, тому в дереві суб-агент стоїть гілкою від
  кореня прогону, а не від того `delegate_to_*`, який його покликав. Щоб було
  друге, довелося б знімати контекст усередині кожного інструмента — а саме там
  його й немає (див. «Дві поломки»). Для вимоги завдання цього достатньо: дерево
  одне, суб-агенти й виклики інструментів у ньому видно.
- **Перевіряти трасування треба ЗА РЕЗУЛЬТАТОМ.** Обидві поломки вище не давали
  ані винятку, ані рядка в лозі. Єдиний надійний спосіб — витягти трейси через
  API і подивитись, чи є в них `session`, `user` і вкладені спани.
