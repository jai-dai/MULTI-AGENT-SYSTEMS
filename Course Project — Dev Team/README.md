# Команда розробки ПЗ: чотири учасники, один із них — людина

Курсова робота. Мультиагентна система, що приймає користувацьку історію й
повертає готовий код із тестами: **Business Analyst → [людина] → Developer ⇄ QA**.

Три агенти на LangGraph, інструменти — через MCP, цикл Developer ⇄ QA побудований
за патерном **Evaluator–Optimizer**: QA не просто ставить оцінку, він повертає
розробнику конкретні зауваження, і той переписує код, доки QA не підпише.

Людина стоїть в одному місці — **між аналітиком і розробкою**. Це найдешевша точка
для втручання: специфікація, ухвалена з помилкою, оплачується всіма ітераціями
розробки, які з неї виростуть.

Текст завдання — у [TASK.md](TASK.md).

Дві речі в цій роботі виявилися важливішими за саму збірку агентів, і обидві
з'ясувалися лише тому, що результат перевіряли вимірюванням, а не читанням логів:

1. **Пісочниця робила задачу нерозв'язною** — не забороняла зайве, а ламала
   штатний Python. Агенти чесно боролися з нею п'ять ітерацій. Розділ нижче.
2. **Чотири з п'яти провалів тестів були дефектами тестової обв'язки**, а не
   системи. Обв'язка не падала — вона впевнено й аргументовано звинувачувала
   справних агентів.

## Швидкий старт

```bash
cd project-dev-team

python3 -m venv .venv && source .venv/bin/activate

cp .env.example .env        # ANTHROPIC_API_KEY / OPENAI_API_KEY
```

```
   користувацька історія
            │
            ▼
      ┌───────────┐   knowledge_search · web_search · read_url
      │    BA     │   (пише специфікацію, але НЕ пише файли)
      └─────┬─────┘
            │  SpecOutput: переказ історії + план робіт
            ▼
      ╔═══════════╗
      ║   ВОРОТА  ║  interrupt() — граф зупиняється
      ║  людина   ║  APPROVE → в розробку
      ╚═════╤═════╝  REVISE  → назад аналітику із зауваженнями
            │
            ▼
      ┌───────────┐   write_file · read_file · list_files · run_python
      │ Developer │◀────────────┐
      └─────┬─────┘             │  зауваження QA
            │ CodeOutput        │
            ▼                   │
      ┌───────────┐             │
      │    QA     │─────────────┘  REVISION_NEEDED (до 5 ітерацій)
      └─────┬─────┘   read_file · list_files · run_python
            │         (НЕ пише файли)
            ▼  APPROVED
       готовий код
```

Стек: LangChain 1.3.16, LangGraph 1.2.11, MCP 1.29.1 / FastMCP 3.4.7,
langchain-mcp-adapters 0.3.2, Langfuse 4.14.5, DeepEval 4.2.0, Qdrant 1.19.0.

### Права ролей — це не зручність, а обмеження

Аналітику **не дано** `write_file`. Аналітик, який може писати файли, починає
писати код замість специфікації, і далі команда узгоджує вже написане, а не
поставлену задачу.

QA **не дано** `write_file` з тієї ж причини в інший бік: рецензент, який може
правити, полагодить сам замість того, щоб сформулювати зауваження — і цикл
Evaluator–Optimizer виродиться в одного агента, що розмовляє сам із собою.

`tools_for()` кидає `KeyError`, якщо роль просить інструмент, якого немає. Мовчазне
пропускання дало б агента, який поводиться дивно, а причина не проявиться ніде.

### Два MCP-сервери

| Сервер | Порт | Інструменти |
|---|---|---|
| **DocsMCP** | 8931 | `knowledge_search`, `web_search`, `read_url` + ресурс `knowledge-base-stats` |
| **WorkspaceMCP** | 8932 | `write_file`, `read_file`, `list_files`, `run_python` + ресурс `workspace` |

База знань — 20 документів (≈1 000 000 символів, у середньому 50 065 на документ):
документація FastAPI, посібник зі стилю Python, матеріали про тестування.
Гібридний пошук + переранжування, як у попередніх роботах.

`_resolve()` у WorkspaceMCP блокує вихід за межі теки: шлях нормалізується й
звіряється з коренем, тож `../../.env` недосяжний.

### Ворота: конкретне слово, а не «будь-що схоже на згоду»

```
👉 APPROVE / REVISE:
```

Приймається **рівно** `APPROVE`. Пробіл, порожній рядок, «К», «ок», Enter — не
згода: система перепитує. Нерозпізнаний ввід **не** трактується як відмова —
інакше випадкова клавіша відкидала б специфікацію на доробку.

Обірваний ввід (`Ctrl-D`, `EOF`) згодою не є теж. Це не педантизм: у попередній
роботі перевіряльник знайшов дефект саме тут — HITL повертав `accept`, тоді як
middleware чекав `approve`, і гілка згоди не спрацьовувала взагалі.

### Специфікації живуть окремою текою

Кожна нова задача — новий файл у `specs/`, ім'я з часу й початку історії:

```
specs/20260831-173404-функція-валідації-email-адреси-з-результ.md
```

Доробка **не створює новий файл**: у той самий дописується `## Версія N`. Тому
історія узгодження задачі читається зверху вниз в одному місці — видно, що людина
відхилила й що аналітик змінив у відповідь.

## Пісочниця, яка робила задачу неможливою

Найдорожча знахідка роботи, і вона не про агентів.

`run_python` виконує код у підпроцесі з обмеженнями пам'яті й часу через
`resource.setrlimit`, а небезпечні модулі блокує. Перша версія робила це двома
прийомами, і **обидва були неправильні**:

- прапорець `-I` (isolated mode) прибирає поточну теку з `sys.path`. Отже, файл,
  який агент щойно написав, **неможливо імпортувати** — ні з тесту, ні з іншого
  модуля;
- блокування `os` було глобальним. Але `os` імпортують `unittest`, `runpy`,
  `tempfile` — тобто ламався не агент, а сам Python.

Пісочниця не забороняла зайве. Вона робила поставлену задачу нерозв'язною.

І тут головне: **нічого не падало з явною помилкою**. Агенти отримували дивні
збої, вважали їх своїми, і чесно намагалися лагодити код.

| | зламана пісочниця | виправлена |
|---|---|---|
| ітерацій | **5** (ліміт вичерпано) | **1** |
| бали QA | 0.70 → 0.75 → 0.70 → 0.72 → **0.60** | **0.92** |
| файлів на виході | **10**, з дублями й `sitecustomize.py` | **2** |

Ті самі промпти, ті самі моделі. Різниця — виключно в інструменті.

Зверніть увагу на траєкторію балів: **0.60 на п'ятій ітерації нижче, ніж 0.70 на
першій**. Команда не просто не сходилась — вона деградувала, обростаючи обхідними
шляхами навколо неіснуючої проблеми. `sitecustomize.py` серед результатів — це
агент, що намагався полагодити інтерпретатор.

Виправлення: блокування перевіряє **кадр викликача**. Якщо `import os` іде з коду
агента — заборона; якщо зі стандартної бібліотеки — дозвіл.

Прапорець `-I` при цьому **лишився** — він корисний іншим: ігнорує `PYTHONPATH` і
змінні середовища, тож підпроцес не бачить оточення хоста. Прибрано не прапорець,
а його побічний ефект: `""` повертається в `sys.path` явно, щоб написані файли
імпортувалися.

**Висновок ширший за цей код: перш ніж покращувати промпти, перевір, що задача
взагалі розв'язна тими інструментами, які ти дав.** Ознака — не помилка, а
дивна впертість моделі там, де задача проста.

## Тести: LLM-as-a-Judge на записаних прогонах

Дорогі прогони пишуться на диск (`tests/capture.py` → `runs/*.json`), тести
оцінюють **записи**. Інакше кожен запуск набору коштував би повного циклу команди.

Суддя — **інший постачальник** (`claude-opus-5` через `tests/judge.py`), бо
оцінювати свою ж роботу тією ж моделлю — не оцінка.

### Базова лінія

```
метрика                     поріг   n   сер    мін   макс   пройшло
-------------------------------------------------------------------
Code Covers Spec              0.7   3   0.93   0.90   1.00    3/3
No Invention                  0.7   1   0.20   0.20   0.20    0/1
Review Completeness           0.7   3   0.90   0.90   0.90    3/3
Review Is Useful              0.7   3   0.83   0.80   0.90    3/3
Solves User Story             0.7   3   0.93   0.90   1.00    3/3
Spec Quality                  0.7   3   0.87   0.80   0.90    3/3
```

**42 тести пройшли, 1 упав.** Той, що впав, — справжній.

### Чотири поломки обв'язки й одна поломка системи

Перший прогін дав два провали. Жоден із них не був тим, чим здавався.

**1. «QA підписав непрацездатний код» — різала обв'язка.**
Суддя писав розгорнуто й переконливо: модуль обірваний на `return _invalid("d`,
він навіть не імпортується, QA поставив APPROVED. Бал 0.30.

Файл на диску був цілий — 4284 символи, коректний кінець. Обрізав його мій же
тест: `content[:4000]` на кожен файл, а поверх ще `context[:14000]`. При цьому
**найбільший прогін займав 8821 символ** — внутрішній ліміт не рятував від
переповнення жодного разу, зате зіпсував 4 файли з 7.

Тест не впав з помилкою. Він **аргументовано звинуватив справного агента**. Якби
я повірив, я б «лагодив» робочий QA.

Виправлено (`tests/context.py`): різати в одному місці, за спільним бюджетом, і
**завжди лишати видиму позначку обриву** — інакше суддя читає кінець бюджету як
обірваний код.

**2. «QA пропустив дефект порядку перевірок» — дефекту не було.**
Після виправлення бал піднявся 0.30 → 0.60, але поріг усе одно не взяв. Суддя
тепер стверджував, що код перевіряє довжину раніше за кількість `@`, і це
відхилення від специфікації.

Специфікація такого не вимагає. Її єдина умова про порядок — щоб він був
**детермінованим**, і код її виконує. Нормативний порядок суддя вичитав із
**порядку пунктів у маркованому списку**, який я йому подав.

**3. Метрика питала одне, а суддя оцінював інше.**
Корінь перших двох. `Review Is Useful` за своїми кроками міряє **якість
формулювань** ревʼю. Але в INPUT я клав увесь код — і суддя, побачивши код,
неминуче йшов перевіряти **повноту** ревʼю, чого жоден крок не просив.

Сигнал про повноту — потрібний. Тому його не викинуто, а винесено в окрему
метрику `Review Completeness`, спитану прямо. Спитана прямо, вона дала **0.90**:
жодної пропущеної вади. Тобто «дефект порядку» був артефактом подачі, і це
підтверджено незалежним вимірюванням, а не міркуванням.

**4. Таблиця балів змішувала свіжі вимірювання з мертвими.**
`runs/_scores.json` зливається з попереднім прогоном — навмисно, щоб запуск
підмножини (`-k`) не стирав решту базової лінії. Але пара «тест + метрика» не мала
терміну придатності: коли тест **змінив метрику**, стара пара лишилась у файлі
назавжди й потрапила у звіт як живе вимірювання.

Виправлено: тест, що відпрацював у цій сесії, **повністю перевизначає** свій набір
метрик, а не доповнює його. Часткові прогони при цьому працюють, як працювали.

**5. І одна справжня: аналітик вигадує предмет.**

Це єдиний провал, що лишився, і він про систему.

На запит **«Зроби щось для роботи з користувачами»** аналітик:

- чесно написав у переказі, що запит надто загальний і що саме треба уточнити ✔
- і **все одно розписав 13 вимог і 7 критеріїв**: CRUD, HTTP 409 на дублікат
  email, HTTP 404, JSON-схему з `created_at`/`updated_at`, soft delete ✘

Тобто застереження зробив, а поведінку не змінив. Три інші історії за метрикою
якості специфікації дали 0.87 — справа саме у винаході предмета.

Спершу цей тест міряли метрикою загальної якості, і бал (0.30) змішував претензії
не по темі. Власна метрика `No Invention` дала **0.20** — різкіше й чесніше.

Пом'якшує це людина: 13 вигаданих вимог видно у воротах, і людина набирає
`REVISE`. Але ціна все одно є — вигаданий обсяг **закріплює** увагу людини на
чужому предметі замість порожнього місця.

### Чому це головний результат тестування

Тести знайшли **п'ять** дефектів. **Чотири з них — у самих тестах.**

Жоден не впав з винятком. Усі п'ять виглядали як провал системи, і всі чотири
хибні супроводжувались розгорнутою переконливою аргументацією судді — саме тому,
що суддя міркував бездоганно **над тим, що я йому дав**.

Правило, яке з цього лишається: **коли LLM-суддя виносить вирок, спершу перевір
його вхід**. Аргументація судді не є доказом, вона є наслідком подачі.

## Спостережуваність

Трасування — Langfuse через OpenTelemetry, перевірене **через API**, не за
виглядом інтерфейсу:

```
трейс: dev-team   сесія: capture-csv-summary   спостережень: 40
коренів: 1

└ dev-team [AGENT]
  └ ba [CHAIN]
    └ model · tools · tools · model
  └ developer [CHAIN]
    └ model · tools · tools · tools · model
  └ qa [CHAIN]
    └ model · tools · tools · tools · model · tools · model
```

До виправлення той самий прогін давав **5 незв'язаних трейсів із коренем `qa`**.
Причина та сама, що й у попередній роботі: **контекст OTel не переживає межу
`async def`**, і кожен вузол починав свій корінь. Лікується тим, що `run_once`
володіє власним кореневим span, у який вкладається все інше.

Ознака дефекту в інтерфейсі — кілька трейсів там, де очікується один. Помилки
немає, дані пишуться, все «працює».

## Обмеження

- **Запис прогонів іде з автопідтвердженням.** Тести перевіряють, що специфікація
  **дійшла** до воріт, а не як система поводиться, коли людина повертає її на
  доробку. Ту гілку тест без людини покрити не може, і вона лишається за межами
  автоматичної перевірки.
- **n=3 для більшості метрик.** Пороги 0.7 — робоча гіпотеза, а не каліброване
  значення. У попередній роботі спроба підняти поріг за одним спостереженням уже
  давала хибний результат; тут поріг свідомо не піднімався.
- **`No Invention` виміряно на n=1.** Дефект відтворюваний і зрозумілий, але
  величина 0.20 — одне вимірювання.
- **Корпус зібрано один раз.** `build_corpus.py` тягне публічну документацію;
  документи не оновлюються й можуть застаріти щодо поточних версій бібліотек.
- **`.env` не публікується**, у репозиторії лише `.env.example`. Приватні імена
  й робочі індекси лишаються локально.
